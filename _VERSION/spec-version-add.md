# spec-version-add — внедрение версионирования сборки

Инструкция для агента. Как встроить механизм версионирования в произвольный
проект. Проектная нейтральность: инструкция не знает, что собирается — книга
Excel, конфигурация 1С, веб-сайт или исполняемый файл. Всё, что зависит от
типа артефакта, сводится к заполнению точек адаптации в одном скрипте.

## Что внедряем

Механизм отвечает на вопросы: «какая версия сейчас установлена» и «из чего
она собрана» — так, чтобы ответ был виден, а не вычислялся сравнением файлов.

Состав механизма:

| Файл | Назначение |
|---|---|
| `install\install.ps1` | объединение install + release: установка/сборка артефакта, хеши исходников, версия, миграции, CHANGELOG |
| `install\install_prod.ps1` | тонкая надстройка: «install с ключами продуктива» — запускает install.ps1 с прод-целью |
| `install\VERSION` | первая строка — версия сборки (SemVer), ниже — описание; ведёт install.ps1 |
| `install\release.state` | служебное состояние прошлого релиза (хеши исходников); ведёт install.ps1 |
| `install\migrations\` | дополнительный код версий, применяемый к артефакту при релизе |
| `CHANGELOG.md` (корень) | накопительный журнал версий; ведёт install.ps1 |

Инвариант: имя файла артефакта версию НЕ несёт. Версия живёт внутри артефакта
и в CHANGELOG, поэтому ярлыки, пути и скрипты не переезжают при каждом релизе.

## Порядок внедрения

Шаги строго по порядку. Всё, что ниже «шага 4», без заполненных точек
адаптации завершится понятной ошибкой, а не молчаливым проходом.

### Шаг 1. Скопировать скрипты в проект

Скопировать `install.ps1` и `install_prod.ps1` в папку `install\` проекта
(папка может называться иначе; важно, чтобы оба скрипта лежали в одной папке,
а корень проекта был её родителем). Файлы обязаны оставаться в кодировке
UTF-8 с BOM — PowerShell 5.1 иначе читает кириллицу как ANSI.

### Шаг 2. Заполнить точки адаптации install.ps1

Найти все вхождения строки `ТОЧКА АДАПТАЦИИ` и заполнить по списку:

| Точка | Что задать |
|---|---|
| `$Target` (параметр) | цель установки по умолчанию: файл артефакта или каталог сборки, путь от корня проекта |
| `$ProjectName` | имя проекта — попадёт в заголовок CHANGELOG.md |
| `$LogFile` | путь журнала; пустая строка = только консоль. Рекомендуется `release.log` рядом со скриптом |
| `$SourceItems` | каталоги и файлы исходников, чьё изменение поднимает версию. Пока список пуст, релиз не стартует |
| строка `[тут код для сборки билда/релиза]` | вызов сборщика/инсталлера проекта; успех = код возврата 0, сбой = ненулевой |
| `$context` | контекст для миграций и записи версии (например, открытый артефакт); открывать здесь, закрывать после записи версии |
| `Read-ArtifactVersion` | чтение версии, уже записанной в артефакте; пустой результат означает 0.0.0 |
| `Write-VersionToArtifact` | запись `BUILD/VERSION`, `BUILD/DATE`, `BUILD/SRC_MD5` в артефакт; при сбое — throw |

Куда писать версию по типам артефактов (принцип, не реализация):

| Тип артефакта | Куда обычно пишут версию |
|---|---|
| Книга Excel | лист настроек: таблица «ключ-значение», ключи `BUILD/VERSION`, `BUILD/DATE`, `BUILD/SRC_MD5` |
| База 1С | константа или регистр сведений; версию печатать в подвал отчёта |
| Веб-приложение | файл `version.json` или аналогичный, читаемый рантаймом |
| Исполняемый файл | версия сборки (ресурс), видимая в свойствах файла |

### Шаг 3. Заполнить точку адаптации install_prod.ps1

- `$Target` — прод-цель по умолчанию (то же значение, что в install.ps1).
  Больше точек нет: install_prod.ps1 сам находит соседний install.ps1
  (объединение install + release) и запускает его с этой целью.

### Шаг 4. Создать служебные файлы

- `install\VERSION` — первая строка `0.1.0` (или текущая версия артефакта),
  ниже описание. UTF-8 без BOM допустим, но лучше тоже с BOM.
- `CHANGELOG.md` в корне — заголовок `# Журнал версий <проект>` и одна строка
  пояснения формата; записи добавит install.ps1.
- `install\migrations\` — пустой каталог.

### Шаг 5. Первый прогон

Из корня проекта, артефакт должен быть закрыт (не открыт в редакторе/базе):

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -DryRun
```

Вывод должен показать `RELEASE_FIRST_RUN` — прошлого состояния нет. Затем тот
же запуск без `-DryRun`. Ожидания первого прогона:

- версия НЕ поднимается: фиксируется та, что записана в VERSION, как точка
  отсчёта;
- в артефакт записываются `BUILD/VERSION`, `BUILD/DATE`, `BUILD/SRC_MD5`;
- применяются все миграции, подходящие по `requires-from`;
- создаются `release.state` и первая запись CHANGELOG.md;
- итоговый маркер: `RELEASE_OK <версия>`.

### Шаг 6. Проверки механизма

Проверочные сценарии (обязательно прогнать все три):

1. **Идемпотентность.** Повторный прогон без изменений исходников → маркер
   `RELEASE_SOURCES_SAME`, версия прежняя, CHANGELOG без дублей.
2. **Патч.** Поменять один исходник, прогон → `RELEASE_SOURCES_CHANGED`,
   версия `+0.0.1`, в артефакте новая версия.
3. **Сбой сборки.** Сломать шаг сборки так, чтобы он вернул ненулевой код →
   маркер `RELEASE_FAIL`, версия, `release.state` и `CHANGELOG.md` НЕ меняются,
   код возврата процесса 1.

Сценарии 1–3 проходят → механизм внедрён. Результат внедрения зафиксировать в
журнале задач проекта: что добавлено и как прогонять.

## Чего не делать при внедрении

- Не подгонять механизм под проект правкой логики версионирования: вся
  специфика — в точках адаптации, ядро (SemVer, state, миграции, CHANGELOG)
  остаётся одинаковым во всех проектах.
- Не вносить версию в имя файла артефакта.
- Не прогонять первый релиз без `-DryRun` и без просмотра вывода.
- Не коммитить `release.state` и `VERSION` с расхождением: эти файлы ведёт
  только install.ps1, руками их не правят.
