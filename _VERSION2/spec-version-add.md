# spec-version-add — внедрение механизма версионирования в проект

Техническая инструкция внедрения. Идёт после опроса владельца
(`spec-version-onboard.md`): все значения уже получены, здесь — куда и что
класть. Проектная нейтральность: сборка конкретного артефакта — в адаптере,
ядро одинаково во всех проектах.

## Что внедряем (состав)

| Файл | Назначение | Правится руками |
|---|---|---|
| `install\install.ps1` | ядро: дайджест, откат, версия, счётчик, миграции, CHANGELOG, манифест | точки адаптации |
| `install\install_prod.ps1` | прод-обёртка | цель `-Target` |
| `install\VERSION` | первая строка — SemVer, ниже — человеческое описание следующего релиза | версия — нет; описание — да, до релиза |
| `install\release.state` | состояние прошлого релиза: хеши + `release_no` | никогда (ведёт ядро) |
| `install\build-info.json` | манифест релиза: `release_no`, `version`, `date`, `digest`, `files[{path, md5}]` | никогда (генерирует ядро) |
| `CHANGELOG.md` (корень) | журнал: человеческое описание → техника | никогда (ведёт ядро) |
| `install\migrations\` | доп. код версий | да, при необходимости |

## Шаги внедрения

1. **Адаптер.** Выбрать готовый из `adapters\` (сейчас есть `excel`) или
   написать новый по `spec-version-contract.md`. Скопировать файлы адаптера
   в проект (например, `install\adapter\`).
2. **Ядро.** Скопировать `install.ps1`, `install_prod.ps1` в `install\`
   (UTF-8 с BOM). Заполнить точки адаптации в `install.ps1`:
   - `$ProjectName` — имя проекта (заголовок CHANGELOG);
   - `$Target` — артефакт по умолчанию;
   - `$SourceItems` — исходники, чьё изменение поднимает версию;
   - `$AdapterDir` — путь к файлам адаптера;
   - `$AdapterType` — метка типа для манифеста;
   - `$LogFile` — журнал или пусто.
3. **VERSION.** Первая строка — текущий SemVer (или `0.1.0`), ниже — заготовка
   описания: инструкция, что вписывать (что добавлено; какая ошибка исправлена;
   что и с каким результатом оптимизировано).
4. **CHANGELOG.** Заголовок `# Журнал версий <проект>` и строка формата:
   «человеческое описание, затем техническая часть; новая запись сверху».
5. **Первый прогон.** Артефакт закрыт. `-DryRun`, читать вывод, затем боевой.
   Ожидания: `RELEASE_FIRST_RUN`, версия фиксируется как точка отсчёта,
   создаются `release.state` (с `release_no = 1` или заданным), `build-info.json`,
   первая запись CHANGELOG.
6. **Приёмка.** Сценарии: идемпотентность (повторный прогон → `RELEASE_SOURCES_SAME`,
   без дублей); патч (правка исходника → `+0.0.1`); сбой сборки (ненулевой код →
   `RELEASE_FAIL`, версия/журнал/манифест не тронуты).

## Правило «где живёт версия» (контролировать при внедрении)

- скрипты-утилиты — версия в шапке;
- рабочий артефакт — штамп внутри (Excel: `CustomDocumentProperties`);
- имя файла — только у неизменяемых снимков/архивов;
- нет внутреннего поля — `version.json` рядом, не имя файла.

## Чего не делать

- Не править ядро под проект: вся специфика — в адаптере и точках адаптации.
- Не переносить версию в имя рабочего файла артефакта.
- Не вести `release.state`, `build-info.json`, `CHANGELOG.md` руками.
- Не релизить при открытом артефакте и без просмотра `-DryRun`.
