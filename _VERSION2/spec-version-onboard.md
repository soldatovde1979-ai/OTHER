# spec-version-onboard — задание агенту: опрос владельца и перенос версионирования

Задание для агента. Цель: внедрить версионирование (`_VERSION2`) в проект
**по результатам опроса владельца**, с нюансами конкретного типа артефакта
(Excel, 1С, веб, exe). Агент ничего не выдумывает: каждая позиция переноса
подтверждается ответом владельца.

## Этап 1. Опрос владельца (обязательный минимум вопросов)

1. **Проект.** Имя проекта (попадёт в заголовок CHANGELOG) и путь к корню.
2. **Продуктив.** Что является продукти-артефактом: файл, папка, база, сервис?
   Где он лежит, на каких машинах им пользуются?
3. **Исходники.** Какие файлы/папки считаются исходниками (их изменение
   поднимает версию)? Входит ли документация в дайджест (по умолчанию да,
   поднимает патч)?
4. **Штамп версии.** Где в артефакте будет жить версия (по правилу из
   `spec-version-contract.md`): поле/свойства внутри (Excel —
   `CustomDocumentProperties`), `version.json` рядом, ресурс сборки. Имя
   файла — только если артефакт является неизменяемым снимком.
5. **Сборка и проверка.** Как собирается/устанавливается артефакт (команда или
   адаптер) и как проверяется успех (код 0; для Excel — компиляция VBA).
   Есть ли готовый адаптер в `adapters\` или нужен новый?
6. **Миграции.** Нужны ли миграции (доделать артефакт сверх установки кода)?
   Какие уже существуют и с какой версии.
7. **Текущая версия.** Какой SemVer сейчас у артефакта (если версий ещё не
   было — `0.1.0`).
8. **Счётчик релизов.** С какого номера считать (если история релизов была —
   следующий за последним; иначе 1).
9. **Кто релизит.** Одна машина или несколько (нужна защита от отката и
   правило git pull → релиз → git push).
10. **Прод-цель.** Целевой артефакт для прод-обёртки `install_prod.ps1`.

Ответы фиксируются кратко, с датой. При неоднозначности агент задаёт уточняющий
вопрос, а не принимает решение сам.

## Этап 2. Перенос в проект (по ответам)

1. Скопировать `install.ps1` и `install_prod.ps1` в `install\` проекта
   (UTF-8 с BOM).
2. Заполнить точки адаптации ядра: `$ProjectName`, `$Target`, `$SourceItems`,
   `$AdapterType`, путь к адаптеру, `$LogFile`.
3. Скопировать выбранный адаптер (`adapters\<тип>\`) в проект; при отсутствии —
   написать новый по `spec-version-contract.md` и положить рядом `spec-<тип>.md`.
4. Создать `install\VERSION`: первая строка — текущая версия, ниже — пустая
   заготовка описания (инструкция из ядра перезапишет при первом релизе).
5. Создать `CHANGELOG.md` с шапкой формата и `install\release.state` не
   создавать — его заведёт первый прогон (`RELEASE_FIRST_RUN`).
6. Первый прогон `-DryRun`, затем боевой. Ожидания: `RELEASE_FIRST_RUN`,
   версия не поднимается, в артефакт пишется штамп, создаются `release.state`,
   `build-info.json` и первая запись CHANGELOG с описанием из VERSION.

## Этап 3. Приёмка (что показать владельцу)

- маркер `RELEASE_OK <версия> (n)` с номером релиза;
- штамп версии в артефакте (для Excel — свойства файла и подвал отчёта);
- `install\build-info.json` — манифест с версиями/хешами файлов релиза;
- запись в CHANGELOG: человеческое описание, затем техника;
- ответ на вопрос «что сейчас стоит в продуктиве» — из штампа артефакта.

## Запреты при переносе

- Не выдумывать пути, ключи и контракты — только из ответов владельца и доков.
- Не переносить версию в имя рабочего файла артефакта.
- Не править руками `release.state`, `CHANGELOG.md`, первую строку `VERSION`.
- Не запускать боевой релиз без `-DryRun` и без просмотра вывода.
