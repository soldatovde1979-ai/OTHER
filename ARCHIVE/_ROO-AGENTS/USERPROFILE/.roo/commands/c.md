# Формат команды

`/c [параметр]` — формулировка параметра может немного плавать. Сначала нормализуй параметр по таблице, затем выполни соответствующий сценарий.

## Нормализация параметра (ищи вхождение ключевого слова в параметре, регистр неважен)

| В параметре есть | Сценарий |
|---|---|
| `push`, `пуш` | push |
| `pull`, `пул` | pull |
| `commit`, `коммит`, `ком`, `комит`, `com` | commit |
| `zoo`, `зу`, `зуу` | zoo-sync |
| `синхр`, `синхрон`, `sync` | sync |
| `сигн`, `sign` | sign |
| `renew`, `ренью` | sig renew |
| параметр пуст | sync |
| ключевое слово не найдено | Параметр — свободная инструкция: прочитай; понятно — выполни, непонятно — уточни у пользователя |

Если в параметре есть `renew`/`ренью` — выполняется сценарий `sig renew`, даже если в параметре есть и другие ключи (`sig`, `sign`, `push` и т.п.).

# Общие правила для всех сценариев

- Факты репозитория: основная ветка `main`, remote `origin`.
- Выполняй git-команды строго по одной, не цепочками; запускай каждую из корня проекта.
- Сценарий zoo-sync работает с репозиторием `%USERPROFILE%\.roo`: все его git-команды — с флагом `-C "%USERPROFILE%\.roo"`; рабочая папка терминала не меняется. Остальные сценарии — из корня проекта.
- Никаких интерактивных редакторов: `commit` только с `-m`, `merge` только с `--no-edit`.
- Rebase и `--force` запрещены.
- При любом merge-конфликте: остановись, выведи `git status` и список конфликтных файлов, ничего не разрешай молча, жди указаний.
- Если merge/pull блокируется незакоммиченными изменениями («would be overwritten by merge»): сначала выполни сценарий commit, затем повтори merge.

# Сценарий 1: commit (коммит)

1. `git add -A` (`.gitignore` отсекает data/, result/, рабочие книги, бэкапы).
2. `git status --short` — если в индексе пусто: выведи «Коммитить нечего»; отдельный сценарий commit на этом завершается (это не ошибка), а в составе push/sync — пропусти коммит и продолжай.
3. Сформулируй сообщение коммита сам, пользователя не спрашивай: кратко, по-русски, по содержанию изменений (что и где), до ~72 символов.
4. `git commit -m "<сообщение>"`.
5. Итог одной строкой: hash коммита и краткий список файлов.

# Сценарий 2: push (пуш, push)

1. Если в `./src/` есть хотя бы один файл `*.sig.md` — выполни сценарий sign (обновление сигнатур) перед коммитом, чтобы в коммит попали актуальные сигнатуры. Нет ни одного — пропусти sign и переходи к шагу 2.
2. Выполни сценарий commit. Если коммитить нечего — пропусти коммит и перейди к push (локальные коммиты могут ждать отправки).
3. `git push origin main`.
4. Если push отклонён («fetch first», расхождение веток):
   - `git fetch`;
   - `git merge origin/main --no-edit` — при конфликте стоп по общим правилам;
   - повторно `git push origin main`.
5. Итог: «Запушено в GitHub», ветка, hash последнего коммита.

# Сценарий 3: pull (пул, pull)

1. `git fetch`.
2. `git merge origin/main --no-edit` — при конфликте стоп по общим правилам.
3. Итог: «Уже актуально» либо число полученных коммитов (hash последнего локального).

# Сценарий 4: sync (синхр, синхрон) — коммит и полный синхрон

1. Выполни сценарий pull (получить изменения с GitHub).
2. Выполни сценарий push (сам вызовет sign перед коммитом, затем коммит и отправку).
3. Итог: получено из GitHub: 
ПОЛУЧЕНО:
   [Описание коммита]
      [список полученных файлов] 
   [Описание коммита]
      [список полученных файлов] 
ЗАПУШЕННО:
    [Описание коммита]
      [список полученных файлов] 

# Сценарий 5: sign — обновление сигнатур

Путь к сигнатурам: `./src/sig/<ИмяМодуля>.sig.md`.

Если файлов `./src/sig/*.sig.md` нет вообще — создать сигнатуру для каждого модуля, найденного в `./src/` и вложенных папках, по шаблону ниже (статус `CLEAN`, дата — сегодняшняя), вывести отчёт о созданных сигнатурах и завершить.

1. Найти все файлы `./src/sig/*.sig.md` со статусом `DIRTY`.
2. Для каждого DIRTY-модуля прочитать полный текущий код модуля (или только изменённую часть, если известно из истории сессии) и переписать сигнатуру по шаблону (все описания должны быть максимально конкреными и понятными без чтения кода):

```markdown
# <ИмяМодуля>

Статус: CLEAN
Обновлено: ДД.ММ.ГГГГ

## Назначение
Одна-две строки - зачем модуль существует.

## Процедуры / Функции

### ИмяПроцедуры(Параметр1, Параметр2 = Знач) : ТипВозврата
- Назначение: зачем процедура/фукнция существует. (одна-две строки дающая максимальное понимание) 
- Вход: что ожидает по смыслу, не только тип + кратко описание параметров
- Выход: что возвращает, кратко, но понятно суть и тип
- Побочные эффекты: запись в регистры, вызов внешних источников, изменение глобальных переменных модуля, обращение к БД. Если их нет — писать "нет побочных эффектов", не пропускать пункт.
```

3. Если модуль помечен `DIRTY`, но при чтении кода изменений по сути не найдено (например, поправили только комментарий) — всё равно пересобрать сигнатуру и снять флаг, не оставлять DIRTY из экономии.
4. В конце — короткий отчёт: какие модули пересобраны, у каких сигнатура не менялась по содержанию (только флаг снят).
5. Если DIRTY-модулей нет — вывести «Сигнатуры актуальны», ничего не делать.

# Сценарий 6: zoo-sync — синхронизация глобальных настроек zoo

1. `git -C "%USERPROFILE%\.roo" remote -v` — origin нет → `git -C "%USERPROFILE%\.roo" remote add origin https://github.com/soldatovde1979-ai/SETTINGs.git`.
2. `git -C "%USERPROFILE%\.roo" fetch` → `git -C "%USERPROFILE%\.roo" merge origin/main --no-edit` (конфликт — стоп по общим правилам).
3. Раскладка эталонов (если в `%USERPROFILE%\.roo\settings-global\` есть файлы): скопировать `custom_modes.yaml` и `mcp_settings.json` в `%APPDATA%\Code\User\globalStorage\zoocodeorganization.zoo-code\settings\`; затем вывести: «Эталоны раскложены — перезапусти окно VS Code (или переключи режим), чтобы zoo-code перечитал настройки».
4. `git -C "%USERPROFILE%\.roo" add -A` → `git -C "%USERPROFILE%\.roo" status --short` пуст → «Коммитить нечего», перейти к push.
5. Сообщение — кратко, по-русски, по содержанию, до ~72 символов; `git -C "%USERPROFILE%\.roo" commit -m "<сообщение>"`.
6. `git -C "%USERPROFILE%\.roo" push origin main`; отклонён («fetch first») → fetch → merge origin/main --no-edit (конфликт — стоп) → повторить push.
7. Итог: получено из SETTINGs / запушено в SETTINGs, hash последнего коммита.

# Сценарий 7: sig renew — полная пересборка всех сигнатур

Путь к сигнатурам: `./src/sig/<ИмяМодуля>.sig.md`.

1. Найти все модули в `./src/` рекурсивно, исключая файлы сигнатур `*.sig.md`.
2. Для каждого модуля прочитать полный текущий код и переписать сигнатуру по шаблону из сценария 5 (статус `CLEAN`, дата — сегодняшняя); если сигнатуры нет — создать.
3. Сигнатуры, у которых модуль в `./src/sig` отсутствует, оставить без изменений и перечислить в отчёте (удалять только по явному указанию).
4. Итоговый отчёт: сколько сигнатур пересобрано, какие созданы, какие не изменились.

# Ограничения

- Не меняй ветку, remote и настройки репозитория — только синхронизация.
- В zoo-sync файлы вне `%USERPROFILE%\.roo` не трогать (кроме раскладки эталонов, шаг 3).
- Не редактируй и не удаляй файлы вне git-операций и обновления сигнатур (сценарии sign и sig renew).
- Не запускай посторонних скриптов — только git-команды сценариев и пересборку сигнатур.
