# _VERSION2 — подсистема версионирования сборки v2

Универсальный механизм версионирования для любого проекта: Excel-книга, база 1С,
веб-приложение, исполняемый файл. Вторая редакция: ядро отделено от сборки
конкретного артефакта — вся специфика вынесена в **адаптеры**.

Правило «одно ядро — много адаптеров»: шаги релиза одинаковы в любом проекте,
отличается только «лютая сборка» конкретного артефакта (для Excel — импорт
VBA/PQ и компиляция). Сборка/проверка/штамп подключаются через контракт
адаптера; новый тип артефакта = новый адаптер по тем же правилам.

## Структура

```
_VERSION2/
├── readme.md                  ← этот файл: карта подсистемы
├── install.ps1                ← УНИВЕРСАЛЬНОЕ ЯДРО релиза (переносится в проект)
├── install_prod.ps1           ← прод-обёртка: запуск ядра с прод-целью
├── doc-version.md             ← обзор для человека: что такое SemVer+счётчик+манифест
├── spec-version-contract.md   ← контракт ядра и адаптеров (обязателен для авторов адаптеров)
├── spec-version-onboard.md    ← ЗАДАНИЕ АГЕНТУ: опрос владельца проекта и перенос
├── spec-version-add.md        ← техническое внедрение в проект
├── spec-version-work.md       ← работа с внедрённым механизмом (порядок релиза, маркеры)
└── adapters/
    └── excel/
        ├── build.ps1          ← сборка книги: VBA-модули + Power Query + шаблон
        ├── verify.ps1         ← пост-проверка + принудительная компиляция VBA
        ├── stamp.ps1          ← штамп в CustomDocumentProperties книги
        ├── context.ps1        ← открыть/закрыть книгу для миграций
        └── spec-excel.md      ← нюансы Excel: прод, сборка, штамп, ограничения
```

## Роли файлов

| Файл | Роль | Переносится в проект |
|---|---|---|
| `install.ps1` | ядро: дайджест исходников → защита от отката → сборка/проверка адаптера → версия + счётчик релизов → миграции → CHANGELOG → манифест | да, в `install\` |
| `install_prod.ps1` | тонкая надстройка: запуск ядра с прод-целью | да, в `install\` |
| `adapters\excel\*.ps1` | сборка/проверка/штамп/контекст книги | да, копией в проект |
| `spec-*.md`, `doc-*.md` | знания и инструкции | нет, остаются здесь |
| `CHANGELOG.md`, `install\VERSION`, `install\release.state`, `install\build-info.json` | создаются в проекте при внедрении, ведутся автоматически | — |

## Как подсистема раскладывается в проекте

Гайды (`spec-*.md`, `doc-version.md`, `example-e2e.md`) остаются в `_VERSION2`;
в проект переносятся только скрипты. После переноса проект выглядит так:

```
<Проект>\
├── CHANGELOG.md                    ← журнал (ведёт install.ps1)
├── <артефакт>                      ← прод (не в git; штамп внутри артефакта)
├── src\...                         ← исходники (что считает исходником — опросник)
├── docs\...                        ← документация проекта
└── install\
    ├── install.ps1                 ← ядро (перенесено из _VERSION2)
    ├── install_prod.ps1            ← прод-обёртка
    ├── VERSION                     ← SemVer (1-я строка) + описание след. релиза (руками)
    ├── release.state               ← хеши + release_no (ведёт install.ps1)
    ├── build-info.json             ← манифест релиза (ведёт install.ps1)
    ├── migrations\*.ps1            ← доп. код версий
    └── adapter\                    ← файлы выбранного адаптера (для Excel: build/verify/stamp/context)
```

Что ведётся руками, а что — ядром, зафиксировано в
[`doc-version.md`](doc-version.md) (таблица «Файлы механизма»).

## Что делает механизм (три слоя)

1. **SemVer** `8.1.9` — для людей: «кто заметит разницу и надо ли ему что-то делать».
2. **Счётчик релизов** `10` — монотонный номер успешного релиза: `8.1.9 (10)`.
3. **Манифест** `install\build-info.json` — прозрачность: какие файлы с какими
   хешами вошли в релиз, читается одним файлом, генерируется при релизе.

Где живёт версия (правило, подробно — в `spec-version-contract.md`):

- скрипты-утилиты — версия в шапке файла;
- рабочий артефакт — штамп **внутри** (Excel: `CustomDocumentProperties`);
- имя файла несёт версию только у неизменяемых снимков/архивов;
- если поля в артефакте нет — `version.json` рядом с ним, а не имя файла.

## Как пользоваться

- Хочешь понять, что это и зачем — [`doc-version.md`](doc-version.md).
- Хочешь увидеть сквозной пример от переноса до релиза (на основе ReportMTO) —
  [`example-e2e.md`](example-e2e.md).
- Хочешь перенести механизм в проект — [`spec-version-onboard.md`](spec-version-onboard.md) (задание агенту: опрос + перенос) и [`spec-version-add.md`](spec-version-add.md).
- Уже внедрено, делаешь релиз — [`spec-version-work.md`](spec-version-work.md).
- Пишешь адаптер под новый тип артефакта — [`spec-version-contract.md`](spec-version-contract.md).

## Статус

Первая редакция v2. Предшественник — `../_VERSION` (моноскрипт с точками адаптации
внутри одного файла). Отличия v2: адаптеры вместо врезки кода в тело ядра,
счётчик релизов, манифест сборки, опросник внедрения.
