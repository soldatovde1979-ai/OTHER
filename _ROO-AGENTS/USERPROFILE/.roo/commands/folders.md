Ты — агент-исполнитель. Язык работы и всех правок — русский. Работай в корне текущего проекта.

# Задача

Привести структуру папок и файлов проекта к универсальному стандарту ниже, настроить правила git и обновить все документы, где описана структура папок.

# 1. Универсальный стандарт структуры

```
<project>/
├── README.md                  ← главный вход: что это, карта папок, как собрать/запустить
├── .gitignore и другие конфиги сборки/инструментов (.vscode/ и т.п.)
├── src/                       ← ТОЛЬКО исходный код (по языкам/подсистемам, например vba/, powerquery/, lib/)
├── tests/                     ← ВСЁ о тестах в одном месте:
│   │                            код тестов, эталоны-ожидания (expected*),
│   │                            тестовые данные (test_*, fixtures/), описание запуска тестов
├── install/                   ← корневая папка: ЕДИНЫЙ пакет — ВСЕ инструкции установки/обновления
├── docs/                      ← ВСЕ документы, по темам:
│   ├── index.md               ← карта документации «что где искать» (создать, если нет)
│   ├── spec.md                ← ОБЯЗАТЕЛЬНЫЙ: спецификация системы
│   ├── data.md                ← ОБЯЗАТЕЛЬНЫЙ: описание данных (источники, форматы, поля)
│   ├── logs.md                ← ОБЯЗАТЕЛЬНЫЙ: журнал работ/ошибок
│   ├── rules.md               ← ОБЯЗАТЕЛЬНЫЙ: память правил и уроков
│   ├── specs/                 ← дополнительные спецификации (архитектура, контракты)
│   ├── presentations/         ← презентации (актуальные версии)
│   ├── plans/                 ← активные планы и задачи исполнителям
│   └── archive/               ← история: выполненные планы, старые версии, handoff-записки
│                                (можно зеркалить структуру папок проекта, откуда взят файл)
├── examples/                  ← примеры входных/выходных файлов, визуальные референсы (лёгкие)
├── tools/                     ← скрипты сборки/тестов/обслуживания (без временных _tmp_*)
├── build/                     ← собранные артефакты (передаётся в git, если политика проекта это требует)
├── data/                      ← входные данные (вне git, только каркас .gitkeep)
└── result/                    ← результаты работы (вне git, только каркас .gitkeep)
```

Правила раскладки:
- Папки верхнего уровня — по ТИПУ содержимого (код / документы / данные / артефакты), внутри `docs/` — по ТЕМЕ.
- Если в папке всего один файл — подпапку не заводить.
- Всё про тесты (код, данные, эталоны, инструкции) — только в `tests/`, нигде больше.
- Документы с версиями в имени: актуальная — в своей тематической папке, старые версии и черновики — в `archive/`.
- Все ТЗ (задания исполнителям) именуются с префикса `tz_` и лежат в `plans/`; выполненные и устаревшие — в `archive/`.
- В `archive/` допускается повторять (зеркалить) структуру папок проекта, откуда перемещён файл,
  например `archive/docs/`, `archive/plans/`, `archive/install/` — так видно происхождение каждого файла.
  Зеркалить только те подпапки, из которых реально есть файлы; пустые каркасы не создавать.
- Глубина вложенности — максимум 2 уровня ниже папки верхнего уровня.

## Обязательные файлы любого проекта

Создай, если отсутствуют, и поддерживай:

| Файл | Назначение | Версионирование |
|---|---|---|
| `README.md` | главный вход: что это, карта папок, как собрать/запустить | да — версия и дата комментарием при существенных изменениях |
| `docs/spec.md` | спецификация системы: что делает, как устроена | да — версия и дата комментарием в начале файла |
| `docs/data.md` | описание данных: источники, форматы, поля, допущения | да — версия и дата комментарием в начале файла |
| `docs/logs.md` | журнал выполненных работ и ошибок | нет — ведётся хронологически |
| `docs/rules.md` | память правил и уроков проекта | нет — короткие императивные правила |
| `docs/tasks.md` | неформализованные задачи проекта | нет - формат ##ЗАДАЧИ <br> [ ] - обновить rules.md <br> ##БЭКЛОГ (в долгую) <br> ##ВЫПОЛНЕНО|

Правила для агента:
- Запиши в `README.md` проекта раздел «Правила для агента: доступ к папкам»: какие папки можно
  читать; куда без явного запроса не ходить (`data/`, `result/`, `docs/archive/` — только
  конкретный файл по имени); что не удалять и не перемещать без согласования.
- Не оставляй мусор в рабочих папках: временные файлы — только в `tools/` с маркером `_tmp_`
  и удаляй их после использования; бэкапы — только в `bak/`; логи — в одно место, определённое
  проектом (не копировать в `build/`).
- Если обязательный документ ведётся вне репозитория (например `docs/spec.md` в проекте Claude),
  файл-заглушку не выдумывать: зафиксировать в `docs/index.md`, где документ живёт.



# 2. Правила git по категориям (обязательно)

| Категория | Режим переноса в git |
|---|---|
| Исходный код (`src/`) | **всё** |
| Тесты (`tests/`) | **всё** |
| Документация (`docs/`) | **всё** (текст всегда в git) |
| Инструкции установки (`install/`) | **всё** |
| Примеры (`examples/`) | **всё**, если лёгкие; тяжёлые данные — в `data/` |
| Скрипты (`tools/`) | **всё, кроме** временных `_tmp_*` / `_*` |
| Артефакты (`build/`) | по политике проекта: либо всё целиком, либо вне git |
| Данные (`data/`), результаты (`result/`) | **только каркас** (`.gitkeep`), содержимое — вне git |
| Локальные рабочие файлы в корне (например, рабочие книги, локальные бинарники) | **вне git** |
| Бэкапы/резервные копии (`*.bak`, `*.bak_*`, `~$*`, копии) | **вне git** — заигнорить, сами файлы НЕ удалять |
| Служебные папки инструментов с общими командами/стандартами (например, `.roo/commands/`) | **в git** (текст, часть стандарта) |
| Секреты, ключи, настройки окружения (`.env` и т.п.) | **вне git**, в `.gitignore` |
| Настройки редактора (`.vscode/`) | только общие; личные — вне git |

После правок `.gitignore` добавь комментарий с версией и датой изменений.

# 3. Алгоритм работы: сначала план, потом работа

**Обязательный порядок: вначале только план и остановка — без одобрения плана пользователем не выполняй перемещения.**

1. Проанализируй текущую структуру проекта: полный листинг папок и файлов.
2. Найди ВСЕ файлы, содержащие пути и перекрёстные ссылки на перемещаемые файлы и папки (документы, скрипты, конфиги — поиском по старым путям). Включи их в план обновления: поправить путь или, если ссылка потеряла смысл, убрать её.
3. Составь и покажи пользователю план: таблицу «текущее место → целевое место» для каждого файла и папки, список кандидатов на удаление (только временные файлы), список файлов, где будут поправлены пути, и план правок `.gitignore`. **Остановись и жди одобрения плана.**
4. После одобрения: создай недостающие папки, проверь обязательные файлы (`docs/spec.md`, `docs/data.md`, `docs/logs.md`, `docs/rules.md`, `docs/tasks.md`), создай отсутствующие.
5. Выполни перемещения по группам (после каждой группы — проверка листингом).
6. Обнови `.gitignore` по таблице раздела 2.
7. Обнови по плану все файлы с устаревшими путями: главный `README.md`, создай `docs/index.md` (карта документации), поправь перекрёстные ссылки и пути внутри скриптов `tools/`.
8. Финальная сверка: полный листинг по папкам, `git status`; подтверди, что ни один файл не потерян и не осталось битых путей.
9. НЕ выполняй `git commit`/`git push` — только подготовь состояние и покажи итоговый `git status`.

# 4. Ограничения и безопасность

- Не переименовывай файлы, имена которых являются контрактами (исходники, шаблоны, конфиги, файлы, вызываемые по имени) — такие файлы можно только перемещать целиком, а при сомнении оставить на месте.
- Удаляй ТОЛЬКО временные файлы (`_tmp_*`, `_*`, `*.bak`, очевидные мусорные копии); всё остальное — перемещай, ничего не удаляй «на всякий случай».
- Не переноси в git большие бинарники и данные — они в `data/`/`result/` вне git.
- Локальные рабочие файлы пользователя не трогай (не перемещай, не удаляй) — только добавь для них игнор.
- При неоднозначности, куда отнести файл, — спроси пользователя, не додумывай.
- При изменении служебных файлов (`.gitignore`) и документов указывай версию и дату комментарием в начале файла; у некритичных инструкций — версию в наименовании.
